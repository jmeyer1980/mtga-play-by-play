# Investigation B — scale measurement

**Date:** 2026-09-04
**For:** condition 4 of [What 1.0.0 means](2026-09-04-1.0.0-definition-design.md)
**Measured on:** the index as built at 0.7.0, 1,399 real matches

## Method

The real `out/index.html` was copied to a scratch directory and never modified. Synthetic
3,000 and 5,000-match indexes were built from it by repeating its real rows, each given a
distinct token in its `data-search` so nothing could be deduplicated and the DOM was
genuinely larger. Nothing touched `out/` or the archive.

All three were served over local HTTP and loaded in a real browser. **The first reading
was discarded**: a cold navigation reported 1,038 ms for the smallest file while the two
larger ones came in at 319 ms and 462 ms, which is a cold-start artefact and not a
measurement. Every number below is warm, taken from a second consecutive load.

## What the file is made of

| part | size | share |
|---|---|---|
| total | 2.84 MB | 100% |
| `<tr>` rows | 2.80 MB | **98.5%** |
| of which `data-search` | 0.93 MB | **32.6% of the whole file** |
| `<script>` | 26.3 KB | 0.9% |
| `<style>` | 10.3 KB | 0.4% |
| everything else | 5.6 KB | 0.2% |

The page is rows and nothing else, and a third of it is the search haystack — a median of
663 characters per row, up to 2,270 for a match where many cards were seen.

## Load

| matches | size | DOM interactive | load event | DOM nodes |
|---|---|---|---|---|
| 1,399 | 2.88 MB | 380 ms | 436 ms | 33,837 |
| 3,000 | 6.00 MB | 988 ms | 1,139 ms | 67,957 |
| 5,000 | 9.90 MB | 2,572 ms | 2,813 ms | 110,653 |

**Growth is superlinear.** Matches ×3.6 from 1,399 to 5,000; interactive time ×6.8. Size
and node count grow linearly at about 2.05 KB and 22 nodes per match, so the extra cost is
in what the browser does with them, not in how many bytes arrive.

## Search

Time from the input event to the filtered result being visible. There is no debounce, so
this cost is paid **per keystroke**.

| term | 1,399 | 3,000 | 5,000 |
|---|---|---|---|
| `plains` | 63 ms | 125 ms | 211 ms |
| `hare apparent` | 166 ms | 533 ms | **655 ms** |
| `nykthos` | 58 ms | 103 ms | 273 ms |
| no match at all | 12 ms | 98 ms | 122 ms |

The handler itself is cheap — 2 to 80 ms in every case. The cost is the layout that
follows it. Typing "hare apparent" at 5,000 matches means thirteen keystrokes each paying
up to 655 ms.

## The horizon is not hypothetical

The archive holds 1,399 matches spanning 2026-08-10 to 2026-09-04 — 25 days, a mean of 56
a day, and 53.6 a day across the last fourteen active days.

At that rate:

- **3,000 matches in about 30 days** — early October 2026
- **5,000 matches in about 67 days** — mid-November 2026

Both thresholds arrive before 1.0 plausibly ships. This is a measurement of the near
future, not of an edge case.

## Does #139 carry it?

#139 is three fixes: a keyed row swap, a search-haystack trim, and an input debounce.

**The debounce is the highest-value change here and should happen regardless.** It does
not make any single filter faster, but it stops paying that cost per keystroke, which is
the difference between a search box that stutters and one that does not.

**The haystack trim removes about a third of the bytes.** That is real, and it reduces
parse time — but bytes are not what makes the curve superlinear.

**The keyed row swap reduces the DOM work each filter does.** Also real, also helpful for
search rather than for load.

**None of the three reduces the node count**, and the node count is what drives the load
curve: 110,653 elements at 5,000 matches, all constructed before the page is interactive,
whether or not any of them will ever be looked at.

So: **#139 is necessary and not sufficient.** It should land, and it will make search
usable. It will not bring a 2,572 ms interactive time under a second, because it does not
change how many rows exist.

## Proposed budget

Set at 5,000 matches, because that is roughly two months away rather than a distant
ceiling:

| metric | budget at 5,000 matches | today |
|---|---|---|
| DOM interactive | **≤ 1,000 ms** | 2,572 ms — 2.6× over |
| search, time to visible result | **≤ 150 ms** | 655 ms — 4.4× over |
| index size | **≤ 12 MB** | 9.90 MB — passes |

Size already passes and is not the problem. The two that fail are both about how much the
browser is asked to do at once.

## Recommendation

1. **Land #139.** Cheap, scoped, and the debounce alone fixes the worst of the search
   experience. Re-measure after.
2. **Expect to need a fourth change**, and treat it as in scope for condition 4: the row
   count itself has to stop being the page's whole cost. Paging, virtualisation, or
   rendering rows on demand from a compact data island rather than as markup — the choice
   wants its own design, and this document does not pick one.
3. **Re-run this measurement after each**, against the budget above, using the same
   method. The scratch harness is reproducible: copy the index, repeat rows with a unique
   token, serve over HTTP, discard the first reading.

Condition 4 is therefore **not** satisfiable by #139 alone. That is the finding this
investigation existed to produce, and it is the reason the spec ordered it before the
index work rather than after.
