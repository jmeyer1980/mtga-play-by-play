# Investigation A — surface audit

**Date:** 2026-09-04
**For:** condition 1 of [What 1.0.0 means](2026-09-04-1.0.0-definition-design.md)
**Version audited:** 0.7.0 (`f726456`)

Every config key, CLI verb and archive file that freezes at 1.0, reviewed for anything
worth changing while it is still cheap. After 1.0 each of these costs a major bump.

## Method

For each surface: is the name right, is the shape right, and would freezing it be a
regret? Verdicts are **keep** (freeze as-is), **decide** (needs a call before the tag) or
**change** (must land before the tag).

Read from the code rather than from memory: config properties and their defaults from
`Config.cs`, verbs from the dispatch table in `Program.cs`, flags from what the parser
actually accepts, archive shapes from the live archive's own files.

## Config keys

| key | type | default | verdict |
|---|---|---|---|
| `LogPaths` | `string[]` | Arena's `Player.log` and `Player-prev.log` | keep |
| `CardDbPath` | `string?` | discovered | keep |
| `ArchiveDir` | `string` | `<home>/archive` | keep |
| `OutputDir` | `string` | `<home>/out` | keep |
| `LocalPlayerUserId` | `string?` | null | keep |
| `OpenAfterBuild` | `bool` | false | keep |
| `SuggestDeckRotation` | `bool` | **true** | keep |
| `MaxArchivedMatches` | `int` | 0 = no limit | keep |
| `ManaLedger` | `bool` | false | keep |

The set is internally consistent: PascalCase throughout, every key mirrored as a nullable
in the `Layer` record so "absent" and "set to the type's default" stay tellable apart, and
the one key whose default is true says so explicitly for that reason. Nothing here reads
like an accident.

Two notes that are not objections:

`MaxArchivedMatches` uses 0 as a sentinel for "no limit". Sentinels usually deserve
suspicion, but the alternative — a nullable — would make the common case require a null
check for no benefit, and 0 is not otherwise meaningful for a cap.

`ManaLedger` and `SuggestDeckRotation` are both **newer than the last release**, so they
have had the least real use of anything on this list. That is the honest weak point of
this audit: a key exercised only by its author is the most likely to be regretted. Neither
shows a problem on reading, and both are simple booleans with an off default or a
documented on default, which is the shape least likely to need changing.

## Config files

The shipped `mtga-pbp.defaults.json` and the user's `mtga-pbp.json`, read in that order so
the user's wins. **Keep.** This split already has a scar to read: #134 was unzipping an
upgrade over the install folder replacing the user's own settings, which is exactly the
failure the two-file design now prevents. It has been tested by the thing it exists to
stop.

## Findings

### 1. `why` requires a full match id — keep, but worth knowing

`mtga-pbp why 6155a8dd` answers `no archived match with id 6155a8dd`. The full 36-character
id is required. This was hit during real use on 2026-09-04, by someone who had the short
id in front of them from a filename.

**Verdict: keep, no pre-1.0 change.** Accepting a unique prefix later is purely additive —
ids that work today keep working — so it does not need to happen before the freeze. Worth
its own issue as an ergonomics improvement, not a blocker.

### 2. `all` is a typeable verb that appears in no documentation — decide

`Program.cs` returns `("all", [])` when no verb is given, and the dispatch table matches
on that string. So bare `mtga-pbp` and `mtga-pbp all` do the same thing, but only the
first is documented.

Freezing it means supporting `all` forever without ever having decided to offer it. Three
options:

- **Document it.** One line in the help. Cheapest, and makes the default action nameable,
  which is occasionally useful in a scheduled task where an explicit verb reads better
  than an empty argument list.
- **Make it internal.** Give the default action a name the dispatch table cannot be
  reached by from the command line, so the surface is exactly what the help says.
- **Leave it.** Freeze an undocumented verb and accept it.

**Recommendation: document it.** It already works, someone's scheduled task may already
use it, and removing a working verb to tidy the surface is the kind of change that costs
a user something for nobody's benefit.

### 3. `logs.json` is keyed by an absolute filesystem path — decide

Its keys are full paths such as `%USERPROFILE%\AppData\LocalLow\Wizards Of The
Coast\MTGA\Player.log`, mapping to that log's startup time and size so the capturer can
tell a rotated log from a grown one.

Two consequences of freezing that shape:

**It orphans.** Move Arena, change drive letter, or run from a different account and the
old key stays in the file forever while a new one appears beside it. Nothing breaks — the
capturer just stops matching the old entry — but the file accumulates dead keys with no
mechanism to notice.

**It embeds the OS username.** Not a leak: the archive is local and never committed, and
the repository rule about usernames is about commits. But the project's own framing is
"static files you own", and an archive is the kind of thing a user might hand to someone
else — at which point `logs.json` carries their Windows account name where the other three
archive files carry none.

Options:

- **Keep.** The path is genuinely the identity of a log file, the file is tiny, and dead
  keys cost nothing but bytes.
- **Key by a stable id** — a hash of the path, or the log's own identity — with the path
  as a value rather than a key. Removes the username from the key space and makes dead
  entries prunable.

**Recommendation: keep, and open an issue.** It is the correct identity for the thing
being tracked, and the failure mode is accumulated bytes rather than wrong behaviour.
The username question is real but belongs to a broader "what does sharing an archive
expose" review, which is a different piece of work than a key rename — the `raw/*.json.gz`
slices carry both players' screen names, so `logs.json` is not where that conversation
starts or ends.

## Outcome

**No surface must change before the tag.** Two want a decision:

| finding | recommendation | blocks 1.0? |
|---|---|---|
| `all` undocumented | document it in `--help` | no — one line, do it any time |
| `logs.json` path keys | keep; open an issue for archive-sharing privacy | no |
| `why` needs a full id | keep; open an ergonomics issue | no |

Condition 1 is therefore satisfiable without redesigning anything, which is the outcome
this investigation existed to establish rather than assume.
